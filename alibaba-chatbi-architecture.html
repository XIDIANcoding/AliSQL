阿里云 Quick BI（智能小Q）组件交互与分层部署架构图

组件名称均取自 InfoQ / 阿里云开发者社区官方演讲与文章 · 按「应用层 / AI 中间层（BI Agent）/ 自研领域模型层 / 知识与建模层 / BI 基座引擎层 / 数据源层」六层展开 · 数字编号为主流程，字母 L / K 为大模型与知识召回总线 · 官方未公开完整架构大图，本图严格按文字描述还原

一、整体组件交互图（按部署位置分层）

数字编号 1~14 为主问数流程顺序；字母 L（紫色）为大模型调用总线、K（琥珀色）为元数据/知识库召回总线。实线为主查询链路，虚线为多步推理回传或反馈。各组件右下角「● LLM / ● 知识召回」徽标表示是否经过 L / K。

1用户提问进入智能小Q；前置处理做权限管控与流量管理（原文，不调大模型）
2领域模型做意图判断；多步任务拆子任务，单步进入核心流程（L）
3实体召回：元数据/枚举值/私域知识/Few-shot/时间戳组装；问题改写补全隐藏信息（K + 改写用 L）
4工程侧组装完整 Prompt，送自研 BI 领域模型
5领域模型生成增强 SQL（单表标准 SQL + 抽象算子：时间/LOD/高级计算）（L）
6自研语法解析器将增强 SQL 稳定转为 DSL，再实例化为 Quick BI 查询参数（确定性，不用大模型）
7（可选）多步计算走 NL2Python Agent：引擎取数后大模型二次推理（虚线，可与引擎交互）
8查询参数进入查询分析引擎（BI 基座，数据库外部）
9引擎展开复杂计算字段（如 LOD→方言 JOIN），并注入用户行列权限
10方言翻译编译器生成目标库物理 SQL（40~50 种方言）
11物理 SQL（及必要内存计算）下发数据源执行
12结果返回引擎；渲染引擎出图；洞察算法/大模型解读可叠加
13图表回流应用层：可交互修改、二次查询、血缘透出（「结果可交互」）
14点赞点踩沉淀 Few-shot / 训练数据飞轮（服务领域模型强化，虚线）
L大模型调用总线：步骤 2 / 3（问题改写）/ 5 / 7（多步）及洞察解读；大小模型双通道
K知识召回总线：步骤 3 的元数据、枚举值、私域知识、样例、建模层字段语义

三、落地开发能力清单（对照腾讯图第三章体例）

若你已有 MySQL + 库内对接大模型，对照阿里链路时：阿里更依赖「自研领域模型 + 抽象算子 + 建模层」；你可用通用模型 + ICL 替代领域微调，用 Cube.js / YAML 指标层替代星型建模，用 SQLGlot 替代自研语法解析器与方言编译，优先走腾讯式 Text2SQL MVP，再逐步补阿里式算子与建模。

阿里组件能力你是否还需开发开源替代
前置权限/流量 · Session · Prompt 编排要FastAPI + Redis/MySQL 会话表
意图判断与任务拆分要（轻量）一次 LLM 调用；LangGraph
元数据/知识/样例召回要（重点）MySQL 元数据表 + FULLTEXT；Vanna 训练库
自研领域模型（预训练+SFT+GRPO）可不必（成本高）复用你已有库内 LLM + ICL
增强 SQL + 抽象算子 + 自研解析器MVP 可简化为 Text2SQL；二期再算子化SQLGlot；Cube.js Query JSON
查询引擎内 LOD 展开 · 40+ 方言单 MySQL 时 可大幅简化SQLGlot；自研轻量同环比模板
行列权限注入要SQLGlot AST 注入；MySQL 视图
AntV 渲染 · Chart Advisor要前端ECharts；@antv/ava（开源）
多步 NL2Python · 洞察算法二期LangGraph + Python；statsmodels
