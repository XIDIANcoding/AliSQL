AliSQL 8.0.44-2 特性部署形态与源码实现分析

0. 总览

文章提到的五项能力可以分为两类：

  • 业务能力：DuckDB 分析引擎、VIDX 向量索引、Native Flashback。
  • 事务提交与日志链路优化：Persist Binlog Into Redo、Binlog Cache Free Flush。
特性 自建 AliSQL 部署形态 RDS 官方部署形态 主要场景
DuckDB 分析引擎 源码构建后以 duckdb_mode=ON 启用；可单实例混部或作为分析节点。 DuckDB 分析主实例；挂载到 RDS MySQL 高可用实例的 DuckDB 分析只读实例。 复杂 JOIN、聚合分析、HTAP。
VIDX 向量索引 内置 vidx daemon 插件，InnoDB 表使用 VECTOR + HNSW。 RDS MySQL 控制台启用向量存储；兼容 MySQL 协议和 SQL。 语义检索、推荐、多模态检索。
Native Flashback 启动 Flashback 任务并设置非零 innodb_undo_retention。 RDS MySQL Native Flashback，使用 AS OF TIMESTAMP。 误更新、误删除后的快速核查与恢复。
Persist Binlog Into Redo 开启 persist_binlog_to_redo，要求特定 binlog/复制参数。 RDS MySQL 参数开启，要求 sync_binlog=1、异步复制等。 小事务高并发提交优化。
Binlog Cache Free Flush 开启 binlog_cache_free_flush，大事务自动准入。 RDS 新实例默认开启；存量实例通过 loose_binlog_cache_free_flush 开启。 大事务提交优化，降低 Binlog 大文件复制阻塞。
重要差异：文章中提到 Free Flush “与实例是否支持 DuckDB 无关”，但 AliSQL 8.0.44-2 源码和仓库 wiki 显示，DuckDB 在开启 binlog 时会注册额外 2PC 参与者，导致 Free Flush 在包含 DuckDB 的构建中通常回退普通 Group Commit。以当前源码逻辑为准。

1. DuckDB 分析引擎增强

1.1 部署形态

RDS DuckDB 分析主实例

独立部署的数据库实例，类似常规 RDS MySQL 主实例，集群系列，一主多备，备份节点可读。

RDS DuckDB 分析只读实例

挂载到常规 RDS MySQL 高可用实例，通过 Row Binlog 同步数据，分析查询资源与主库隔离。

[mysqld]
duckdb_mode=ON
duckdb_memory_limit=2147483648
duckdb_threads=0
duckdb_temp_directory=/path/to/duckdb-tmp
CREATE TABLE sales (
  id BIGINT PRIMARY KEY,
  region VARCHAR(32),
  amount DECIMAL(18,2)
) ENGINE=DuckDB;

SELECT region, SUM(amount)
FROM sales
GROUP BY region;

1.2 使用方式、效果与性能

维度 自建 AliSQL RDS MySQL
启用方式 启动前设置 duckdb_mode=ON（启动后只读）；可选 duckdb_memory_limit、duckdb_threads、duckdb_temp_directory。建表 ENGINE=DuckDB 或 ALTER TABLE ... ENGINE=DuckDB。 创建 DuckDB 分析主实例（独立集群，一主多备）；或在 MySQL 高可用实例上添加 DuckDB 分析只读实例（Binlog 原生复制，资源与主库隔离）。
使用方式 应用仍用 MySQL 协议连接；分析 SQL 路由到 DuckDB 引擎执行，结果经 Result Translator 转回 MySQL 格式。只读拓扑通过 Row Binlog 从 InnoDB 主库同步。 分析查询直连 DuckDB 实例/只读节点；TP 流量保留在常规 RDS MySQL 主实例，实现 HTAP 资源隔离。
预期效果
  • 列式存储 + 向量化执行，显著加速扫描、JOIN、聚合类查询。
  • 列式压缩降低分析节点存储占用（实际压缩率需用业务数据测量）。
  • SQL 高度兼容 MySQL（官方称 >99.9%），多数查询零改写即可执行。
  • 只读分析节点不占用事务主库 CPU/内存，保障 OLTP 稳定性。
官方性能数据
  • RDS 官方：复杂分析查询性能百倍跃升；相同数据量 SUM 等聚合查询响应时间可缩短至 InnoDB 的 1/100（约 100 倍）；复杂查询较 InnoDB 提升约 2 个数量级。
  • AliSQL Wiki TPC-H SF100（32C/128GB/ESSD，方向性参考）：多项查询 DuckDB 耗时 0.1–1.6s，InnoDB 数十秒至超时（1800s）；已完成查询普遍200 倍以上加速。总耗时 DuckDB 15.31s vs InnoDB 25234.31s。
适用场景 实时聚合分析（日志/报表）、多表 JOIN 复杂查询、需要 MySQL 生态的一体化 HTAP、希望降低独立 OLAP 运维成本。
注意事项
  • 延迟敏感的事务写入应保留在 InnoDB；分析负载建议只读节点隔离。
  • 不支持跨引擎混合查询；DuckDB 表需 duckdb_require_primary_key。
  • Wiki 基准为方向性参考，非性能承诺；RDS 指标不能直接套用于自建版本。
  • 小事务高频复制可能产生延迟，需调 duckdb_multi_trx_in_batch 等批量参数。

来源：阿里云 RDS DuckDB 分析实例；AliSQL Wiki duckdb-zh.md。

1.8 约束与缺陷

  • 不支持 DuckDB 表与其他引擎表混合查询。
  • DuckDB 不原生支持 MySQL 2PC，AliSQL 做了专用提交、回放、恢复协议。
  • 小事务高频复制到 DuckDB 可能产生复制延迟，需要 batch 参数调优。
  • SQL 兼容不是完整 MySQL，DDL、函数、数据类型、collation 需要业务验证。
  • 单实例混部存在资源竞争，生产分析场景更推荐只读分析节点隔离。

2. VIDX 原生向量索引

2.1 部署形态

  • 自建 AliSQL：内置 vidx daemon 插件，默认关闭。
  • RDS MySQL：控制台启用向量存储，支持最高 16,383 维，兼容 MySQL 协议、JDBC、ORM、DTS、DMS、备份恢复。
SET GLOBAL vidx_disabled = OFF;
SET SESSION transaction_isolation = 'READ-COMMITTED';

CREATE TABLE documents (
  id BIGINT PRIMARY KEY,
  content TEXT,
  embedding VECTOR(3)
) ENGINE=InnoDB;

CREATE VECTOR INDEX idx_embedding
ON documents(embedding)
M=6 DISTANCE=COSINE;

SELECT id,
       VEC_DISTANCE_COSINE(embedding, VEC_FROMTEXT('[0.1,0.2,0.3]')) AS distance
FROM documents
ORDER BY distance
LIMIT 10;

2.2 使用方式、效果与性能

维度 自建 AliSQL RDS MySQL
启用方式 SET GLOBAL vidx_disabled = OFF;；会话级 SET SESSION transaction_isolation = 'READ-COMMITTED';。建表使用 VECTOR(N) 列，CREATE VECTOR INDEX 创建 HNSW 索引。 控制台 → 基本信息 → 运行状态 → 向量存储 → 开启（动态生效，无需重启）。参数在参数设置页修改 vidx_* 系列。
使用方式
  • 插入：VEC_FROMTEXT('[...]') / TO_VECTOR 写入向量。
  • 检索：ORDER BY VEC_DISTANCE(vector_col, query_vec) LIMIT K，可与标量 WHERE 组合。
  • 调优：M（图连接数）、DISTANCE（EUCLIDEAN/COSINE）、vidx_hnsw_ef_search、vidx_hnsw_cache_size。
预期效果
  • 最高 16,383 维浮点向量，与业务标量字段同表存储。
  • HNSW 近似最近邻 + SIMD（含 AVX-512）+ Bloom Filter 剪枝，大规模向量检索效率显著提升。
  • 完全兼容 MySQL 协议，支持 JDBC/ORM、DTS/DMS、备份恢复，无需独立向量数据库。
  • 向量距离排序与标量过滤可在单条 SQL 内完成混合查询。
官方性能数据 官方文档未公布统一 TPS/QPS 基准，强调检索效率与混合查询能力。性能取决于向量维度、数据规模、M/ef_search 及缓存命中，需用业务数据压测验证。
适用场景 语义检索、RAG 知识库、智能推荐、多模态相似度搜索、需要向量+业务字段联合过滤的 AI 应用。
注意事项
  • 仅 InnoDB 表；隔离级别必须 RC；主键长度 ≤256 字节。
  • 建/改/删向量索引不能用 INPLACE；索引不可 INVISIBLE。
  • HNSW 含随机性，主备图结构不保证逐字节一致。
  • 索引维护消耗额外存储与 CPU；NULL 向量不写入索引。

来源：阿里云 RDS 向量存储；AliSQL Wiki vidx_readme_zh.md。

2.9 约束与缺陷

  • 仅支持 InnoDB 表。
  • 要求 Read Committed 隔离级别。
  • 不支持 ALGORITHM=INPLACE 和 invisible vector index。

3. Native Flashback

3.1 部署形态

[mysqld]
innodb_rds_flashback_task_enabled=ON
innodb_undo_retention=3600
innodb_rds_flashback_interval=1
SELECT id, status
FROM orders AS OF TIMESTAMP DATE_SUB(NOW(), INTERVAL 5 MINUTE)
WHERE customer_id = 1001;

RDS 官方说明：Native Flashback 使用 AS OF TIMESTAMP 查询历史版本，消耗额外 Undo 表空间，不保证结果与指定时间点完全匹配。

3.2 使用方式、效果与性能

维度 自建 AliSQL RDS MySQL
启用方式 启动前同时配置 innodb_rds_flashback_task_enabled=ON 与 innodb_undo_retention>0（二者缺一后台线程可能不创建）。可选 innodb_rds_flashback_interval 控制快照间隔。 控制台开通 Native Flashback；服务侧管理保留策略与 Undo 空间。MySQL 8.0 内核小版本 ≥20210930。
使用方式
  • 查询历史：SELECT ... FROM t AS OF TIMESTAMP '2026-07-16 10:00:00' 或 DATE_SUB(NOW(), INTERVAL 5 MINUTE)。
  • 恢复：先 CREATE TABLE recovered LIKE t，再 INSERT INTO recovered SELECT * FROM t AS OF TIMESTAMP ...，核对后 RENAME TABLE（需停写）。
  • 运维：CALL dbms_admin.analyze_flashback_snapshots() / show_flashback_snapshots / del_flashback_snapshots。
预期效果
  • 误 UPDATE/DELETE 后秒级核查历史行，无需 Binlog Flashback 或备份恢复。
  • 基于周期性快照 + Undo MVCC，在保留窗口内直接一致性读历史版本。
  • 相比备份恢复：节省额外机器与不可控的恢复时间，降低运维复杂度。
官方性能数据 官方未提供量化 TPS/延迟提升。价值体现在恢复时间（RTO）与操作复杂度：简单 SQL 即可查历史，避免数小时级备份回放。代价是额外 Undo 表空间与 Purge 压力；innodb_undo_retention 越大，可查询窗口越长、空间占用越高。
适用场景 误操作快速核查、定向数据恢复、审计“某时刻数据长什么样”、替代复杂 Binlog 回滚的轻量场景。
注意事项
  • 仅 InnoDB 基表 SELECT；不支持视图、临时表、FOR UPDATE。
  • 结果取最接近指定时间的快照，非精确匹配（innodb_rds_flashback_allow_gap 控制容差）。
  • 跨 DDL（如删表）不可查；不能替代备份与容灾演练。
  • Undo 保留是目标值，空间阈值或负载压力可能缩短实际窗口。

来源：阿里云 RDS Native Flashback；AliSQL Wiki native-flashback-zh.md。

4. Persist Binlog Into Redo

4.1 部署形态

[mysqld]
sync_binlog=1
innodb_flush_log_at_trx_commit=1
binlog_order_commits=OFF
replica_preserve_commit_order=OFF
persist_binlog_to_redo=ON

RDS 官方说明：Binlog in Redo 将事务 Binlog 内容同步写入 Redo Log，减少磁盘同步 I/O 次数；Binlog 文件格式不变，复制和第三方工具不受影响。

4.2 使用方式、效果与性能

维度 自建 AliSQL RDS MySQL
启用方式 启动前配置：sync_binlog=1、innodb_flush_log_at_trx_commit=1、binlog_order_commits=OFF、replica_preserve_commit_order=OFF、persist_binlog_to_redo=ON。duckdb_mode 激活时会被拒绝。 设置 persist_binlog_to_redo=ON、binlog_order_commits=OFF、异步复制；sync_binlog=1。MySQL 8.0 内核 ≥20200430。
使用方式
  • 符合条件的事务：Binlog Event 写入 Redo，前台仅等待一次 Redo fsync；后台线程异步写 Binlog 文件并按 sync_binlog_interval 批量同步。
  • 崩溃恢复：从 Redo 重建 Binlog 尾部，保证文件完整性。
  • 不符合准入（超大事务、多 2PC 引擎、需提交顺序等）自动回退普通 Group Commit。
预期效果
  • 将前台双同步 I/O（Binlog + Redo）合并为单次 Redo 同步，降低提交延迟。
  • 批量 GTID 处理减少高并发锁竞争；Binlog 格式不变，复制与第三方工具无感。
  • 云盘场景下同步 I/O 开销更明显，收益通常更大。
官方性能数据
  • RDS Sysbench（32C/128GB/ESSD，高可用异步复制）：oltp_update_non_index 与 oltp_write_only 开启后 TPS 在低并发与高并发均明显提升，延迟降低。
  • 并发特征：<64 并发提升显著；>256 并发峰值更高、延迟更低，更好承接流量突增。
  • 用例差异：单语句事务多的 oltp_update_non_index 提升幅度大于多语句的 oltp_write_only（提交次数更多，双 I/O 消除收益更大）。
适用场景 sync_binlog=1 + innodb_flush_log_at_trx_commit=1 的强持久化 OLTP；高并发写入、云盘存储、对提交延迟敏感的业务。
注意事项
  • 单事务 Binlog Cache 需 ≤ persist_binlog_to_redo_size_limit（默认 1 MiB）。
  • Clone 临时要求提交顺序时会回退；DuckDB 激活时不可用。
  • wait_binlog_flush 改变提交可见性，需结合持久化策略压测。
  • 物理备份恢复到自建库需 RDS 版 XtraBackup（本地盘实例）。

来源：阿里云 RDS Binlog in Redo；AliSQL Wiki binlog-in-redo-zh.md。

4.9 约束与缺陷

  • 并非所有事务都会走优化路径。
  • 大事务、非事务表、statement cache、提交顺序要求都会回退。
  • 后台化不是消除 I/O，而是转移前台等待。
  • Redo 压力、Binlog flush 延迟、buffer 大小需要监控。
  • 需要重点验证 crash recovery 和复制一致性。

5. Binlog Cache Free Flush

5.1 部署形态

SET GLOBAL binlog_cache_free_flush_limit_size = 268435456;
SET GLOBAL binlog_cache_free_flush = ON;

RDS 官方文档说明：新建实例默认开启，存量实例通过 loose_binlog_cache_free_flush 开启；默认阈值 256 MB。

5.2 使用方式、效果与性能

维度 自建 AliSQL RDS MySQL
启用方式 SET GLOBAL binlog_cache_free_flush = ON;；SET GLOBAL binlog_cache_free_flush_limit_size = 268435456;（256 MiB，下限 10 MiB）。要求仅 Binlog + InnoDB 两个 2PC 参与者（含 DuckDB 构建会回退）。 新建实例默认开启；存量实例设 loose_binlog_cache_free_flush=ON。阈值 loose_binlog_cache_free_flush_limit_size 默认 256 MB。MySQL 8.0/5.7 内核 ≥20240731。
使用方式
  • 事务 Binlog Cache 超过阈值后溢写临时文件；提交时将临时文件直接 rename 为 Binlog，避免持锁期间二次完整复制。
  • 临时文件头部预留 File Header、Format/Previous GTID、Empty event 等空间，提交时补齐。
  • 不满足条件（加密、Incident、多 2PC 等）自动走普通 Group Commit。
预期效果
  • 大事务提交不再长时间占用 LOCK_log，实例不会长时间不可写。
  • 消除大事务引发的 IO 风暴与小事务排队，避免 TPS 剧烈抖动和连接数雪崩。
  • 提交耗时与 Binlog Event 数量解耦，大文件 rename 远快于逐 Event 复制写入。
官方性能数据
  • 优化前（RDS 案例）：COMMIT 平均耗时 1.64s（2104 次）；大 UPDATE 平均 4.3s、最大 57s、锁等待 1.7s。
  • Sysbench 混合负载：每 5s 执行一次产生 512 MB Binlog 的大 UPDATE 时，优化前 TPS 剧烈下跌；优化后大 UPDATE 对 TPS 几乎无影响。
  • 延迟：即使 Binlog >512 MB，其他事务提交延迟未受明显干扰。
适用场景 批量导入/大 UPDATE/DELETE、Binlog Event 量大的事务、与在线小事务混部且需避免提交抖动的生产环境。
注意事项
  • 当前 AliSQL 构建含 DuckDB 时因额外 2PC 注册会回退（与 duckdb_mode 无关）。
  • Binlog 加密一定回退；转化文件默认关闭 checksum、多一个 Empty event（复制兼容）。
  • 参数开启≠事务一定走优化路径，需用超过阈值的大事务压测验证。

来源：阿里云 RDS Binlog Cache Free Flush；AliSQL Wiki binlog-cache-free-flush-zh.md。

5.9 DuckDB 交互差异

当前源码中，Binlog_cache_free_flush::check() 会检查 2PC 参与者数量。 DuckDB 在开启 binlog 时注册 prepare，会导致多一个非 binlog 2PC 引擎。 因此包含 DuckDB 的构建通常会让 Free Flush 回退普通 Group Commit。

7. 重点风险与验证建议

特性 重点风险 建议验证
DuckDB SQL 兼容、DDL 行为、复制延迟、资源竞争、2PC 交互。 用业务 SQL 回放；压测 Row Binlog 同步；验证故障恢复。
VIDX ANN 召回率、写放大、缓存大小、RC 隔离要求。 用真实向量数据测试召回/延迟；监控辅助表和缓存。
Native Flashback Undo 空间、Purge 压力、跨 DDL 不可读、快照偏差。 按目标保留窗口压测 Undo；演练误操作恢复流程。
Binlog in Redo 崩溃恢复、Redo 压力、后台 Binlog flush 延迟。 做 crash injection；验证复制位点和 Binlog 完整性。
Free Flush 多 2PC 引擎回退、加密回退、rename 崩溃窗口。 构造大事务压测；验证 DuckDB 构建中的实际准入；做重启恢复测试。
总体判断：AliSQL 8.0.44-2 同时改动 SQL Parser、Optimizer、Handler、InnoDB MVCC/Undo、 Binlog Group Commit、Redo Recovery、复制 Apply 与存储引擎插件体系。最需要关注的是 DuckDB 与 Binlog/2PC 的组合、Binlog in Redo 的崩溃恢复、VIDX 的 HNSW 一致性维护，以及 Flashback 对 Undo/Purge 的长期影响。
